# 3. 자원 노드 휴면

## 요약

자원 노드에 `DORM_DormantAll`을 주고, 채집과 재생성으로 상태가 바뀔 때만 `FlushNetDormancy()`로 깨워 보내게 했습니다. 같은 시나리오로 세 번 측정하니 서버 프레임 시간이 17.64ms에서 14.69ms로 16.7%, 리플리케이션 시간이 13.14ms에서 10.17ms로 22.6% 줄었습니다. 줄어든 것은 채널이 열려 있던 노드를 프레임마다 확인하던 비용이고, 네트워크 드라이버 자체 시간(프레임당 9.43ms)은 대부분 남았습니다. 연결당 열린 액터 채널 수는 118에서 20으로 줄었지만, 클라이언트에 존재하는 노드 수는 114에서 301로 오히려 늘었습니다. 휴면에 들어간 노드는 플레이어가 멀어져도 클라이언트에 남기 때문입니다.

### 변하지 않는 노드를 매 프레임 확인합니다

②의 `LabResourceNode` Count 1,083,238은 연결 하나가 프레임마다 노드 75.4개를 처리한다는 뜻입니다(1,083,238 ÷ `WorldTick` 1,797 ÷ 연결 8. 세 실행에서 75.4\~95.6개). 컬 거리 안에 있어 채널이 열린 노드를, 바뀐 것이 있는지 프레임마다 하나씩 확인하는 비용입니다. 이 타이머가 프레임당 1.74ms(`GameNetDriver`의 13.15%, 세 실행에서 1.74\~1.98ms)입니다.

![적용 전 r3 Connection 0 Outgoing 측정 구간의 Net Stats](images/before-network.png)

① `Actor`와 `LabNpc`의 비트, ② `LabResourceNode`의 비트, ③ 고른 측정 구간입니다.

그런데 같은 60초 동안 `Connection 0`으로 실제로 나간 노드 데이터는 27번, 1,314비트뿐입니다(②). 노드의 상태는 채집할 때와 재생성될 때만 바뀌고, 그 일은 검증용 노드 하나에서만 일어납니다. 8개 연결을 합쳐 100만 번 넘게 확인했고, `Connection 0`에 보낸 것은 27번입니다. 이동하는 `Connection 1`은 새로 컬 거리 안에 들어온 노드를 받느라 145번이었습니다. 확인 자체를 하지 않게 만드는 것이 휴면이 겨냥한 자리입니다.

### `GameNetDriver` 자체 시간은 이 트레이스로 나뉘지 않습니다

리플리케이션 시간의 79\~82%(프레임당 10.43\~10.80ms)는 `GameNetDriver`의 Exclusive입니다. 고려 목록 만들기, 연결마다의 거리 검사, 우선순위 정렬, 송신이 섞여 있고, 이 가운데 노드 때문에 드는 몫이 얼마인지는 이 트레이스로 알 수 없습니다.

## 선택

휴면은 포스팅 1에서 두 번째로 골랐습니다([포스팅 1의 "선택"](../01-baseline/README.md#선택)). 그때의 이유는, 관련성을 되돌려도 노드 5,001개 × 연결 8개의 거리 검사가 남는데 휴면이 노드를 활성 목록에서 빼서 그 몫을 줄인다는 것이었습니다.

**이 기대는 틀렸습니다.** 포스팅 3을 측정하기 전에 엔진 소스를 다시 읽고 알았습니다. 노드가 활성 목록에서 빠지려면 모든 연결에서 휴면이어야 하는데(`Engine/Source/Runtime/Engine/Private/NetworkObjectList.cpp:348-376`), 연결별 휴면은 그 연결에 열린 액터 채널을 통해서만 등록됩니다(`Engine/Source/Runtime/Engine/Private/DataChannel.cpp:2354, 2461, 2728`). 관련성을 적용한 뒤에는 한 노드에 채널을 여는 연결이 가까이 있는 몇 개뿐이라, 8개 연결 모두에서 휴면이 되는 노드는 거의 없습니다. 포스팅 1은 "모든 연결에서 휴면 상태가 된 노드는 활성 목록에서 빠진다"까지는 맞게 읽었지만, 이 시나리오의 노드가 그 조건을 채우지 못한다는 것을 놓쳤습니다.

그래서 측정 전에 기대를 고쳐 잡았습니다. 휴면이 줄이는 것은 채널이 열린 노드의 확인(위 "관찰"의 프레임당 1.74\~1.98ms)이고, 거리 검사가 들어 있는 `GameNetDriver` 자체 시간은 대부분 남을 것으로 봤습니다. 포스팅 2의 예고 문장도 이 내용으로 고쳤습니다.

그래도 계획대로 진행했습니다. 순서는 포스팅 1에서 이미 정했고, 효과가 작더라도 "휴면이 무엇을 줄이고 무엇을 줄이지 못하는가"를 재서 보여 주는 것이 이 포스팅의 내용이라고 판단했습니다.

## 적용

`LabResourceNode`의 생성자에서 휴면 상태를 정하고, 서버에서 상태를 바꾸는 두 함수의 첫머리에서 깨웁니다. 다른 코드는 바꾸지 않았습니다.

```diff
 // Source/DSOptLab/LabResourceNode.cpp
 ALabResourceNode::ALabResourceNode()
 {
 	PrimaryActorTick.bCanEverTick = false;
 	bReplicates = true;
 
+	// 상태가 바뀔 때만 깨워서 보낸다.
+	NetDormancy = DORM_DormantAll;
+
 	Mesh = CreateDefaultSubobject<UStaticMeshComponent>(TEXT("Mesh"));
```

```diff
 void ALabResourceNode::Harvest()
 {
 	if (!HasAuthority() || bDepleted)
 	{
 		return;
 	}
 
+	// 휴면 중이면 깨워서 아래 변경이 전송되게 한다.
+	FlushNetDormancy();
+
 	--Health;
```

```diff
 void ALabResourceNode::Respawn()
 {
+	FlushNetDormancy();
+
 	Health = MaxHealth;
```

**휴면은 연결마다, 채널을 통해서 정해집니다.** 레거시 리플리케이션에서 `DORM_DormantAll`인 액터는 채널이 열려 초기 상태가 전송된 뒤, 그 연결에서 휴면에 들어가고 채널이 닫힙니다(`ShouldActorGoDormant`는 채널이 없으면 false, `Engine/Source/Runtime/Engine/Private/NetDriver.cpp:5506-5526`). 그 뒤로 서버는 이 연결에 대해 이 액터를 건너뜁니다(`NetDriver.cpp:5618-5624`). `FlushNetDormancy()`는 휴면을 풀어 바뀐 프로퍼티가 한 번 전송되게 하고, 액터는 다시 휴면에 들어갑니다(`NetDormancy` 값은 그대로입니다. `Engine/Source/Runtime/Engine/Classes/GameFramework/Actor.h:3176-3178`).

**활성 목록에서 빠지지는 않습니다.** 서버가 프레임마다 도는 고려 목록은 활성 목록에서 만들어지고(`NetDriver.cpp:5315`), 액터가 활성 목록에서 빠지는 것은 모든 연결에서 휴면이 됐을 때입니다(`Engine/Source/Runtime/Engine/Private/NetworkObjectList.cpp:348-376`). 연결별 휴면은 액터 채널에서만 등록되는데(`Engine/Source/Runtime/Engine/Private/DataChannel.cpp:2354, 2461, 2728`), 관련성을 적용한 뒤에는 한 노드에 채널을 여는 연결이 가까이 있는 몇 개뿐입니다. 그래서 이 시나리오의 노드는 거의 모두 활성 목록에 남고, 채널이 없는 연결마다 거리 검사(`NetDriver.cpp:5580-5593`)를 계속 받습니다. 맵에 미리 놓인 `DORM_Initial` 액터만 예외로 처음부터 빠지는데(`NetDriver.cpp:5369-5378`), 이 프로젝트의 노드는 실행 중에 스폰합니다.

이 시점의 코드는 태그 [`post-03-dormancy`](https://github.com/hon454/ue-dedicated-server-optimization-lab/tree/post-03-dormancy)에 있습니다.

## Iris에서는

> 실행해 보지 않은 내용입니다. 언리얼 엔진 5.8.3 소스에서 읽은 범위만 적었습니다.

Iris에서는 액터의 `NetDormancy`가 객체 하나의 "휴면을 원함" 비트로 전달되고(`FReplicationSystemUtil::NotifyActorDormancyChange` → `SetObjectWantsToBeDormant`, `Engine/Source/Runtime/Engine/Private/Net/Iris/ReplicationSystem/ReplicationSystemUtil.cpp:672-687`), 이 비트가 켜진 객체는 프레임마다의 폴링 대상에서 빠집니다(`net.Iris.UseDormancyToFilterPolling` 기본값 true, `Engine/Source/Runtime/Net/Iris/Private/Iris/ReplicationSystem/ObjectReplicationBridge.cpp:77-80, 2075-2080`). `FlushNetDormancy()`는 그 객체를 한 번 폴링하게 합니다(같은 파일 `2083-2098`). 소스대로라면 레거시처럼 연결마다 채널을 거쳐 휴면에 들어가는 구조가 아니라서 이 포스팅에서 남은 비용의 모양이 다를 텐데, 얼마나 다른지는 모릅니다.

- **노드 직렬화가 사라졌습니다.** `LabResourceNode` 타이머 호출이 60초에 609번입니다(관련성 `r1`은 997,693번). 연결 하나가 프레임마다 처리하는 노드가 95.6개에서 0.043개가 됐습니다(609 ÷ 1,788 ÷ 8). 채집으로 상태가 바뀐 노드만 깨어나 전송됩니다.
- **`GameNetDriver` 자체 시간은 대부분 남았습니다.** 1.00ms 줄었지만 세 실행의 범위(9.32\~10.60ms)가 관련성의 범위(10.43\~10.80ms)와 겹쳐, 줄었다고 확정할 수 없습니다. 휴면인 노드도 활성 목록에 남아 연결마다 거리 검사를 받는다는 소스의 내용과 맞는 결과입니다.

## 한계와 다음

- **휴면은 이 시나리오에서 거리 검사를 줄이지 못했습니다.** 포스팅 1에서는 휴면이 노드 5,001 × 연결 8의 확인을 줄일 것으로 기대했지만, 관련성을 적용한 뒤에는 노드가 모든 연결에서 휴면이 되지 못해 활성 목록에 남습니다. 줄어든 것은 채널이 열린 노드(연결당 약 98개)의 직렬화뿐입니다. 남은 `GameNetDriver` 자체 시간(프레임당 9.43ms)을 줄이려면 노드가 고려 목록에 들어오지 않게 해야 하고, 이 시리즈의 세 기법 밖입니다.
- **`GameNetDriver` 자체 시간의 내역을 여전히 모릅니다.** 거리 검사, 우선순위 정렬, 송신이 섞여 있습니다. 1.00ms 줄어든 것이 실제 변화인지도 이 측정으로는 가릴 수 없습니다.
- **휴면 노드가 클라이언트에 쌓입니다.** 위 "정확성 확인"의 동작입니다. 이 실험은 90초라서 300개 남짓이지만, 오래 돌아다니면 맵의 노드를 모두 갖게 됩니다. 해결은 이 포스팅에서 구현하지 않았습니다.
- **`r1`이 다른 두 실행보다 11\~17% 느렸습니다.** 이유를 확인하지 않았습니다. 이 때문에 변동 폭이 관련성 때보다 크고, P99와 연결당 송신 대역폭은 구별되는 차이가 아닙니다.
- **연결당 송신 대역폭은 `r2`의 `Connection 0` 하나만 읽었습니다.** 제자리에서 채집하는 연결이라 이동하는 연결과 다를 수 있습니다.
- **측정 조건이 하나 달랐습니다.** 측정 PC에는 두 구성 모두 원격 데스크톱으로 접속해 있었는데, 휴면을 측정할 때의 원격 화면 크기(1728×1084)가 관련성 때와 달랐습니다. 서버 수치에 영향이 있었는지는 확인하지 않았습니다.
- 에디터 빌드, 같은 PC의 서버와 클라이언트, 루프백 네트워크 같은 측정 환경의 한계는 [테스트베드와 측정 방법](../00-testbed/README.md)의 "한계"에 있습니다.

**다음: AI NPC 업데이트 빈도.** 이제 클래스 타이머로 보이는 비용은 NPC 직렬화(프레임당 0.41ms, 리플리케이션 시간의 4.0%)이고, 송신 비트의 71.9%가 NPC 이동입니다. 포스팅 4에서는 NPC의 `NetUpdateFrequency`를 낮춰, 서버가 NPC를 리플리케이션 대상으로 고려하는 횟수를 줄입니다. 겨냥하는 CPU 비용이 서버 프레임 시간의 변동 폭(2.13ms)보다 작아서 시간 지표로는 차이가 구별되지 않을 수 있고, 대역폭 쪽에서 차이가 날 것으로 봅니다.
