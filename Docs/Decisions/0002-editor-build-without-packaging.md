# ADR-0002: 패키징과 null RHI 없이 에디터 빌드로 측정한다

- 상태: 승인됨
- 날짜: 2026-10-01
- 출처: [설계 문서](https://github.com/hon454/ue-dedicated-server-optimization-lab/blob/post-04-update-frequency/Docs/Planning/2026-10-01-short-term-portfolio-design.md) 2절, 8.5절

## 맥락

이 포트폴리오의 이전 시도들은 계획 단계로 되돌아가곤 했다. 원인 가운데 둘이 패키징과 null RHI였다. 코드를 고칠 때마다 쿠킹과 패키징을 기다려야 해서 반복이 느렸고, 클라이언트 화면이 없어 최적화로 무엇이 달라졌는지 보여 줄 시각 자료가 부족했다.

## 결정

서버와 클라이언트 모두 에디터 빌드 실행 파일을 쿠킹 없이 실행한다. 서버는 `-server -log`, 클라이언트는 `-game -windowed`로 띄운다. 클라이언트는 실제로 렌더링하고, 그 화면(화면 위 글자, 내려다보기 화면, 자동 스크린샷)을 포스팅의 시각 자료로 쓴다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 패키징한 서버(Windows 또는 Linux) | 코드를 고칠 때마다 쿠킹과 패키징이 필요해 반복이 느려진다 |
| null RHI 클라이언트 | 메모리와 CPU는 덜 쓰지만 화면이 없다. 클라이언트가 실제로 받은 액터를 그림으로 보여 줄 수 없다 |

## 결과

- 빌드 한 번, 스크립트 한 번으로 측정까지 간다.
- 에디터 빌드라 절대 수치가 출시 빌드와 다르다. 수치는 같은 조건의 전후 비교로만 해석하고, 이 한계를 테스트베드 포스팅과 README에 적는다.
- 렌더링하는 클라이언트 8개가 서버와 같은 PC를 쓴다. 서버와 클라이언트를 서로 다른 코어에 고정해 클라이언트 부하가 서버 수치에 섞이는 것을 줄인다([ADR-0008](0008-reproducible-runs.md)).
- 쿠킹하지 않은 클라이언트 하나가 맵을 읽기 전에 이미 약 2.5GB를 써서(`client0-smoke1-r1.log`) 클라이언트 수가 PC 메모리에 묶인다.
- 패키징한 서버로의 재측정은 백로그에 있다.
