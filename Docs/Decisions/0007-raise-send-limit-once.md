# ADR-0007: 기준선이 포화되면 송신 한도를 올려 한 번만 고정한다

- 상태: 승인됨
- 날짜: 2026-10-01 (사용자 결정)
- 출처: [설계 문서](https://github.com/hon454/ue-dedicated-server-optimization-lab/blob/post-04-update-frequency/Docs/Planning/2026-10-01-short-term-portfolio-design.md) 8.1절 기준선 조건, [구현 계획](https://github.com/hon454/ue-dedicated-server-optimization-lab/blob/post-04-update-frequency/Docs/Planning/2026-10-01-short-term-implementation-plan.md) 태스크 8.4, 8.4a, 8.6, [engine-notes.md](../Reference/engine-notes.md) 가절 "한도가 정해지는 과정", 바절 "대역폭 예산과 서버 틱"

## 맥락

엔진 기본 송신 한도는 연결당 초당 100,000바이트다(`BaseEngine.ini:1839-1840, 1860-1861`). 실측 전 추정으로 기준선은 연결당 약 135\~180KB/s가 필요하다(NPC 300명 × 초당 30회 × 한 번에 15\~20바이트, 계산값). 기준선이 포화될 가능성이 높다.

이 시리즈는 서버 처리 비용의 전후 비교를 보여 주려는 것이다. 포화 상태에서는 서버가 한도에 걸린 연결의 리플리케이션을 중간에 끊어 기준선 비용이 실제보다 작게 나오고, 최적화 뒤에 대역폭이 오히려 느는 식으로 결과를 설명하기 어려워진다.

## 결정

기준선이 포화되면(`saturated_ratio` 0.01 이상, [ADR-0006](0006-saturation-from-engine-analytics.md)) 프로젝트 설정에서 연결당 송신 한도를 올린다. 에이전트는 다시 묻지 않고 진행한다.

1. 세 키를 함께 올린다: `[/Script/Engine.Player] ConfiguredInternetSpeed`(클라이언트가 읽는다), `[/Script/OnlineSubsystemUtils.IpNetDriver] MaxClientRate`와 `MaxInternetClientRate`(서버가 읽는다). 엔진 설정 파일은 고치지 않는다.
2. 규모를 정하는 동안에는 초당 10,000,000바이트로 둔다.
3. 규모가 정해진 뒤 한 번만, 30Hz로 환산한 송신량의 약 두 배로 고정한다. 환산 송신량 = `out_bytes_per_sec_per_conn` × 30 ÷ (`frames` ÷ 측정 초).
4. 이후 포스팅에서는 바꾸지 않는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 포화된 상태를 기준선으로 받아들이기 | 기준선 비용이 실제보다 작게 나와 전후 비교를 해석할 수 없다 |
| 실측 송신량을 그대로 기준으로 두 배 | 기준선은 30Hz를 지키지 못해 움직이는 액터의 송신량이 작게 실측된다. 최적화로 30Hz가 돌아오면 두 배를 넘을 수 있다 |
| 구성마다 한도 조정 | 구성 사이의 조건이 달라져 기준선부터 다시 재야 한다 |
| 한도를 사실상 없애기(10,000,000 그대로) | 두 배로 여유를 두되 한도가 없는 것과 같은 값은 피한다 |

## 결과

- 네트워크가 루프백이라 한도를 올려도 부작용이 없다.
- 기준선은 엔진 기본 송신 한도가 아닌 조건에서 잰 것이다. 올린 값, 환산식, 이유를 테스트베드 포스팅과 측정의 한계에 적는다.
- 변하지 않는 노드는 틱이 올라가도 바이트가 거의 늘지 않으므로 환산값은 실제보다 클 수 있다. 한도가 넉넉해지는 쪽이라 포화를 피한다는 목적에는 안전하다.
- 포화를 먼저 없앤 뒤에 예산 초과를 판단한다(태스크 8.4의 순서). 포화 상태의 `work`로 판단하면 규모를 잘못 키운다.
- 기본 한도에서의 포화와 우선순위(`NetPriority`)는 백로그의 별도 포스팅으로 다룬다.
