# ADR-0008: 실행을 재현 가능하게 만들고, 3회 중앙값과 실패 규칙으로 판정한다

- 상태: 승인됨
- 날짜: 2026-10-01
- 출처: [설계 문서](../Planning/2026-10-01-short-term-portfolio-design.md) 8.1절 "재현성", 8.2절, [구현 계획](../Planning/2026-10-01-short-term-implementation-plan.md) 태스크 6, 7

## 맥락

서버와 클라이언트 8개가 한 PC에서 돈다. 접속 순서, 난수, 클라이언트의 렌더링 부하, OS 스케줄링이 실행마다 달라지면 같은 구성도 수치가 흔들린다. 그 흔들림을 최적화 효과로 잘못 읽지 않아야 하고, 사람 없이 에이전트가 실행 결과를 믿을 수 있어야 한다.

## 결정

**같은 실행을 만든다.**

- 노드와 NPC 배치는 고정 시드로 생성한다(`-LabSeed=`, 기본 20261001).
- 클라이언트는 실행 인자로 자리 번호를 받는다(`-LabSlot=`). 접속 순서에 따라 위치가 바뀌지 않는다.
- 모든 클라이언트가 준비되면 서버가 공통 시작 신호를 낸다. 이동, 채집, NPC 배회, 자동 스크린샷의 시계가 이 신호에서 출발한다.
- 클라이언트는 고정 경유점을 따라 자동 이동하고, 하나는 검증용 노드를 반복 채집해 약 26초 주기의 상태 변화를 만든다.
- 클라이언트는 저해상도 창과 30fps 제한으로 실행한다.
- 서버는 논리 프로세서 0\~7(선호도 마스크 `0xFF`), 클라이언트는 나머지에 고정한다(`Scripts/run-scenario.ps1`).
- 스크립트 하나가 서버와 클라이언트를 모두 띄우고 끝나면 모두 종료한다.

**같은 방법으로 판정한다.**

- 접속 완료 뒤 준비 구간을 버리고 측정 구간만 잰다.
- 구성마다 3회 실행해 중앙값을 기록하고, 세 값과 변동 폭(최댓값 - 최솟값)을 모두 적는다.
- 중앙값의 변화가 두 구성의 변동 폭 중 큰 쪽보다 클 때만 차이가 있다고 쓴다. 그보다 작으면 "구별하지 못했다"고 쓰고 두 구성을 한 번 더 잰다.

**실패한 실행은 버린다.**

- 시작 신호 뒤(준비 구간 포함)에 연결 수가 바뀌면 서버가 CSV를 쓰지 않고 종료 코드 1로 끝난다. 스크립트가 그 실행을 실패로 처리한다.
- 같은 라벨은 다시 쓰지 않는다. 스크립트가 로그와 트레이스 파일로 재사용을 막는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 1회 측정 | 한 번의 이상치를 걸러 내지 못한다 |
| 평균 | 이상치 하나에 끌려간다 |
| 모든 차이를 효과로 보고 | 같은 구성의 흔들림보다 작은 차이를 효과로 오해한다 |
| 연결이 빠진 실행도 기록 | 연결 하나가 빠지면 송신 바이트 합계와 서버 부하가 함께 줄어 최적화 효과처럼 보인다 |

## 결과

- 실패 처리가 실제로 동작했다. `smoke6-r1`에서 측정 구간 29.5초에 클라이언트 창 하나가 닫혀 서버가 `Run failed: connection count changed after start`로 종료 상태 1을 냈고, CSV 행이 남지 않았다.
- 3회 반복은 이상치를 거르지만 지속적인 경합이나 실행 순서의 영향까지 없애지는 못한다. 코어를 나눠도 캐시와 메모리 대역폭 경합은 남는다. 이 한계를 테스트베드 포스팅과 README에 적는다.
- 큰 효과는 3회로 충분하고, 작은 효과에만 추가 측정을 쓴다.
