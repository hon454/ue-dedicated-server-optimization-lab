# 2막 설계: 테스트베드 확장과 그 뒤의 포스팅

작성: 2026-10-03. 결정은 [ADR-0014](../Decisions/0014-act-2-testbed-expansion.md)에 있고, 이 문서는 그 내용을 풀어 쓴 것이다. 태스크는 [구현 계획](2026-10-03-act-2-implementation-plan.md)에 있다.

## 1. 1막과 2막

- **1막**은 포스팅 0\~4다. 플레이어 캐릭터, 자원 노드, AI NPC 세 요소의 테스트베드에서 레거시 리플리케이션에 Relevancy, Dormancy, Net Update Frequency를 차례로 적용했다. 글과 태그(`post-00-testbed`\~`post-04-update-frequency`), 수치는 그대로 둔다.
- **2막**은 포스팅 5부터다. 테스트베드를 한 번 확장해 새 기준선을 잡고, 1막의 세 기법을 그 위에 약식으로 다시 적용한 뒤, 새 기법과 시스템(Push Model, FastArray, Replication Graph, Iris 등)을 하나씩 다룬다.
- 2막의 수치는 1막의 수치와 직접 비교하지 않는다. 시나리오가 다르다. 둘을 잇는 것은 "세 기법 다시 적용" 포스팅 하나다.

## 2. 확장하는 이유

2막의 목표는 포스팅마다 적용한 기법이 구별되는 변화를 보이는 것이다(2026-10-03 사용자 결정). 지금 테스트베드에는 그 재료가 부족하다.

| 사실 | 근거 |
| --- | --- |
| 세 기법 적용 뒤 서버 프레임 시간 평균이 13.16ms로 틱 예산 33.3ms의 40%다 | `update-frequency3`, 루트 README "누적 수치". 13.16 ÷ 33.3 |
| 남은 리플리케이션 시간 8.73ms의 95.0%(8.29ms)가 `GameNetDriver` Exclusive 한 덩어리다 | [포스팅 4](../../Posts/04-update-frequency/README.md) "결과"의 표 |
| Push Model이 줄일 "바뀐 것이 있는지 확인하는 비용"이 최종 구성에 거의 없다 | Dormant 상태의 자원 노드는 `LabResourceNode` 타이머가 프레임당 0.007ms(`dormancy2-r2`, [포스팅 3](../../Posts/03-dormancy/README.md) "결과"). NPC는 보낼 때마다 위치가 바뀐다 |
| 송신 한도 포화와 `NetPriority`를 볼 조건이 없다 | `update-frequency3`의 `out_bytes_per_sec_per_conn` 2,400은 엔진 기본 한도 100,000바이트/초의 2.4%다(2,400 ÷ 100,000) |
| 플레이어끼리 만나지 않는다 | 자리 간격 약 196m(2π × 500m ÷ 16, `LabScenarioConfig.h`의 `PlayerRingRadius`, `NumPlayerSlots`)가 Net Cull Distance 150m보다 크다. 이동 경로는 한 변 100m의 정사각형이다(`LabPlayerController.h`의 `WaypointSide`) |
| 인벤토리, 건축물처럼 backlog.md의 주제가 쓰는 요소가 없다 | [README.md](../../README.md) "테스트베드 한눈에 보기" |
| 포스팅 4에서 이미 서버 프레임 시간 평균이 구별되지 않았다 | 루트 README "기법별 변화" |

## 3. 확장 요소

네 요소를 한 번에 넣는다. 기준선이 한 번만 바뀌고, 세 기법을 다시 적용하는 측정도 한 번이다.

| 요소 | 비용 패턴 | 재료가 되는 포스팅 |
| --- | --- | --- |
| 플레이어가 모이는 배치 | 연결마다 다른 플레이어의 캐릭터 무브먼트를 받는다 | NPC 보간, 지연과 패킷 손실, `NetPriority` |
| 상태 값 | 계속 움직여 Dormant 상태가 될 수 없는 액터의, 드물게 바뀌는 값 | Push Model |
| 인벤토리 | 플레이어마다 가진 큰 배열. 채집하면 한 칸이 바뀐다 | FastArray, 소유자 전용 전송 |
| 건축물 | 플레이어 주변에 밀집한 정적 액터. Net Cull Distance 안에 몰려 있다 | Consider List, Replication Graph, Iris, 초기 전송 |

모든 요소에 공통인 원칙이다.

- **C++로 실행 시 생성한다.** 에디터 작업은 없다.
- **요소마다 실행 인자를 두고 기본값을 끔으로 한다.** 인자 없이 실행하면 1막의 시나리오가 그대로 재현되어야 한다. 새 프로퍼티는 하위 클래스나 별도 컴포넌트에 두어, 인자를 주지 않은 실행의 리플리케이션 구성이 바뀌지 않게 한다(영상용 `ALabShowcaseNpc`와 같은 방식). 재현은 주장하지 않고 측정으로 확인한다(구현 계획 태스크 19).
- **고정 시드로 배치하고 공통 시작 신호에서 출발한다.** 1막과 같다([ADR-0008](../Decisions/0008-reproducible-runs.md)).
- **클라이언트 화면 글자에 새 요소의 수를 더한다.** 클라이언트에 존재하는 건축물 수 같은 값이 전후 비교의 시각 자료가 된다.
- **기준선에서는 최적화를 하지 않는다.** [ADR-0003](../Decisions/0003-lawless-baseline.md)의 방식 그대로, 새 액터도 기준선에서는 Always Relevant이고 Dormant 상태가 아니며 Net Update Frequency가 엔진 기본값이다.

### 3.1 플레이어가 모이는 배치

플레이어 자리의 간격을 Net Cull Distance 안으로 좁히는 서버 인자를 둔다. 지금은 반지름 500m의 원 위 16자리이고, 인접한 자리가 약 196m 떨어져 있어 Relevancy 적용 뒤에는 다른 플레이어의 캐릭터가 리플리케이트되지 않는다.

- 정할 것: 여덟 명이 모두 서로의 Net Cull Distance 안에 있게 할지, 일부만 모을지. 모두 모으면 연결마다 캐릭터 일곱 개를 받고, 플레이어 주변의 노드와 NPC 집합이 서로 겹친다.
- 확인하지 않은 것: 캐릭터 무브먼트의 리플리케이션 비용이 이 규모(연결 8개)에서 변동 폭보다 큰지.

### 3.2 상태 값

NPC와 플레이어에 드물게 바뀌는 리플리케이트 프로퍼티를 여러 개 둔다(체력, 상태 같은 것). 서버가 시드로 정한 간격에 따라 일부 액터의 값만 바꾼다.

- NPC는 계속 움직여서 Dormancy의 대상이 아니다. 이동은 보낼 때마다 바뀌지만 상태 값은 대부분의 프레임에서 그대로라, "바뀐 것이 있는지 확인하는 비용"이 최종 구성에도 남는다.
- 정할 것: 프로퍼티의 수와 바뀌는 빈도. 보정에서 정한다.
- 확인하지 않은 것: `AActor`의 기본 프로퍼티 가운데 Push Model이 아닌 것은 항상 바뀐 것으로 취급된다(`RepLayout.cpp:1506`). 어느 프로퍼티가 해당하는지 보지 않았다.

### 3.3 인벤토리

플레이어마다 아이템 배열을 가진다. 시작할 때 고정 시드로 채우고, 채집 RPC가 성공하면 한 칸의 수량이 바뀐다. 기준선에서는 일반 `TArray` 프로퍼티이고 조건 없이 리플리케이트한다.

- 정할 것: 배열을 어느 액터에 둘지. `APlayerState`는 엔진 기본값이 Always Relevant이고 Net Update Frequency가 1이다(`PlayerState.cpp:26, 28`). 여기에 두면 기준선에서 모든 연결이 모든 플레이어의 인벤토리를 받는다. 캐릭터에 두면 Relevancy를 따른다.
- 채집하는 클라이언트가 지금은 0번 자리 하나다. 인벤토리가 바뀌는 연결을 늘릴지는 보정에서 정한다.

### 3.4 건축물

플레이어 자리 주변에 정적 액터를 고정 시드로 밀집 배치한다. 체력 같은 프로퍼티를 가지고 거의 변하지 않는다.

- 자원 노드와 다른 점은 밀도다. 자원 노드는 맵 전체에 흩어져 Relevancy 적용 뒤 연결당 열린 액터 채널이 118개로 줄었다(`relevancy2`). 건축물은 Net Cull Distance 안에 몰려 있어 Relevancy만으로는 줄지 않는다.
- 정할 것: 실행 중에 플레이어가 설치하는 동작을 넣을지. 넣으면 Dormant 상태에서 깨우는 경로와 초기 전송을 다룰 수 있다.

## 4. 기법 전환 인자

1막의 세 기법은 생성자에 고정돼 있다(`LabResourceNode.cpp:17`의 `NetDormancy = DORM_DormantAll`, `LabNpc.cpp:17`의 `SetNetUpdateFrequency(10.f)`, 지운 `bAlwaysRelevant = true` 두 줄). 지난 구성을 재려면 태그를 빌드해야 하는데, 태그에는 [ADR-0012](../Decisions/0012-server-timer-resolution.md)의 수정이 없어 지금 빌드와 조건이 다르다.

세 기법을 서버 실행 인자로 켜고 끌 수 있게 한다. 인자를 주지 않으면 지금과 같이 세 기법이 모두 적용된 구성이다. 2막에서 더하는 기법도 인자를 두고 기본값을 끔으로 해서, 인자 없는 실행이 언제나 1막의 최종 구성이 되게 한다. 2막의 구성은 `run-scenario.ps1`의 매개변수로 지정한다. 한 바이너리에서 구성만 바꿔 연달아 잴 수 있어야 "같은 화면 조건에서 연달아 잰 묶음끼리 비교한다"는 규칙(STATUS.md "명령")을 지킬 수 있다.

## 5. 새 기준선과 보정

규모(새 요소의 수, 필요하면 자원 노드와 NPC의 수)는 보정 실행으로 정한다. 클라이언트 수는 8로 둔다. 확정 규모에서 UE 프로세스 9개의 메모리 합계가 27.5GB였고(`calib-a-r1`), null RHI를 쓰지 않으므로([ADR-0002](../Decisions/0002-editor-build-without-packaging.md)) 부하는 연결 수가 아니라 플레이어 주변의 액터 밀도로 올린다.

확정 조건은 두 묶음이다.

1. **기준선의 네 조건**(1막과 같다): 초기 전송 완료, 지속적인 틱 예산 초과, 가장 큰 비용이 네트워크, 송신 한도에 포화되지 않음.
2. **세 기법을 적용한 구성의 조건**(2막에서 더한다): 예정된 기법마다 겨냥할 비용이 `work_avg_ms`의 변동 폭보다 크다. 겨냥할 비용은 Insights의 클래스 타이머나 Network Insights의 비트 수로 읽는다.

2번을 더하는 이유는, Always Relevant 기준선이 지금도 프레임당 198.43ms라 그쪽만 보고 규모를 맞추면 뒤 포스팅의 재료가 보장되지 않기 때문이다.

**송신 한도.** 새 기준선이 지금 한도 350,000바이트/초에 포화되면 [ADR-0007](../Decisions/0007-raise-send-limit-once.md)과 같은 계산(기준선 송신량을 30Hz로 환산한 값의 약 두 배)으로 한 번 더 올려 2막 동안 고정한다.

**효과를 만들어 내지 않는다.** 겨냥할 비용이 있는 환경을 만드는 것까지가 설계다. 기법을 적용한 결과가 "구별되지 않음"이면 그대로 쓴다.

## 7. 2막에서 다루지 않는 것

backlog.md에 남긴다.

- 서버 틱 최적화(애니메이션, 물리, AI). NPC는 2막에서도 움직이는 리플리케이트 액터의 대역이다. 기준선의 조건 "가장 큰 비용이 네트워크"를 유지한다.
- Test 패키지로 재측정, 다른 OS에서의 프로파일링. 측정 신뢰도의 주제이고 [ADR-0002](../Decisions/0002-editor-build-without-packaging.md)를 대체하는 결정이 따로 필요하다.
- 실행 사이 흔들림의 원인.
