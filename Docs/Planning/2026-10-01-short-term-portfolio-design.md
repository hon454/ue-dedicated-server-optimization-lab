## 2. 작업 규칙

이전 시도들이 계획 단계로 되돌아간 원인(패키징과 null RHI로 인한 느린 반복, 시각 자료 부족, 여러 기법의 동시 적용)을 막기 위한 규칙이다.

1. **패키징하지 않는다.** 서버와 클라이언트 모두 에디터 빌드 실행 파일을 쿠킹 없이 실행한다. 서버는 `-server -log`, 클라이언트는 `-game -windowed`.
2. **null RHI를 쓰지 않는다.** 클라이언트는 실제로 렌더링하며, 그 화면이 포스팅의 시각 자료다.
3. **포스팅 하나에 기법 하나.** 다른 기법이 떠오르면 [backlog.md](backlog.md)에만 적는다.
4. **포스팅 하나에 git 태그 하나.** `post-01-baseline` 형식.
5. **확정된 결정은 다시 열지 않는다.** 아래 3절의 결정을 바꾸고 싶으면 단기 범위가 끝난 뒤에 논의한다.

### 기준선("무법지대")의 정의

레거시의 `AActor` 기본값에는 이미 컬 거리가 있어서, 아무 설정 없이 만든 액터도 거리 기반 관련성 판정을 받는다. 기준선에서는 자원 노드와 AI NPC에 `bAlwaysRelevant = true`를 주어 이 기본값을 의도적으로 끈다. 포스팅 1에 이 사실과 이유("모든 것을 모든 플레이어에게 보낸다"는 가장 단순한 구현을 출발점으로 삼기 위함)를 명시하고, 포스팅 2에서 기본값을 되살린다. 컬 거리 값을 조정하는 것은 별개의 실험이라 백로그에 둔다.

이 기준선은 인위적인 출발점이다. 포스팅 2의 개선은 "엔진 기본 동작의 복원"이고, 그 뒤 포스팅들이 "기본 동작 위의 개선"이다. 포스팅과 README에서 이 둘을 구분해 적는다.

## 7. 포스팅 틀

모든 포스팅이 같은 순서를 따른다.

1. **요약**: 한 문단과 전후 수치 표
2. **관찰**: Insights 스크린샷과 함께, 무엇이 가장 큰 비용인지
3. **선택**: 후보 기법들과, 이것을 고른 이유(구현 비용 대 기대 효과)
4. **적용**: 핵심 코드 변경과 태그 링크
5. **Iris에서는**: 같은 목적을 Iris에서 달성하는 방법의 짧은 예고. 실행해 보지 않은 내용임을 표기한다. Iris 전환 후 실측으로 교체한다.
6. **결과**: 같은 시나리오로 재측정한 수치와 스크린샷, 클라이언트 화면에서 달라진 점
7. **한계와 다음**: 이 측정이 말해주지 않는 것, 다음 포스팅 예고

포스팅에 쓰는 모든 수치와 설정값에는 근거를 함께 적는다. 근거의 종류는 셋 중 하나다: 직접 측정한 값(측정 조건 명시), 엔진 소스에서 확인한 값(파일과 심볼 명시), 계산으로 얻은 값(식 명시).

## 8. 측정 규약

### 8.1 시나리오

아래 값은 출발값이다. 2일차에 기준선 조건(아래)을 만족하도록 조정한 뒤 고정하고, 조정 과정과 최종값을 포스팅 0에 적는다. 이후 포스팅에서는 바꾸지 않는다.

| 항목 | 출발값 | 근거 |
| --- | --- | --- |
| 서버 틱 | 30Hz (틱 예산 33.3ms) | 엔진의 `NetServerMaxTickRate` 기본값이 30이라는 것은 이전 버전 기준 기억값이다. 1일차에 5.8.3 소스와 실행 중 프레임 수로 확인한다. 1000ms ÷ 30 = 33.3ms. |
| 맵 크기 | 바닥 2km × 2km, 배치 영역 1.9km × 1.9km | 엔진 기본 컬 거리(150m)의 원 면적은 π × 150² ≈ 70,700m²로 배치 영역 3,610,000m²의 약 2.0%다. 관련성 판정의 효과가 뚜렷하게 나오는 크기다. |
| 클라이언트 | 8개 | CPU 32스레드와 RAM 64GB를 서버와 나눠 쓴다. 쿠킹하지 않은 클라이언트 하나가 RAM 2~4GB를 쓴다고 추정하면 8개가 16~32GB다. 2일차에 실측해 조정한다. |
| 자원 노드 | 5,000개 + 검증용 1개 | 기준선에서 연결당 고려 대상이 약 5,300개, 8연결이면 틱당 약 42,400쌍이다. 이것은 고려 대상의 수이고 실제 직렬화 횟수가 아니다. 변하지 않는 노드는 정상 상태에서 거의 바이트를 보내지 않는다. 균등 배치 시 가장자리가 아닌 위치에서 컬 거리 안의 기대 개수는 5,000 × 70,700 ÷ 3,610,000 ≈ 98개다(계산값이며 실측값과 구분해 적는다). |
| AI NPC | 300명 | 계속 움직이는 액터가 노드와 구별되는 비용으로 보일 만큼의 수. 2일차에 Insights에서 확인해 조정한다. |

엔진 기본값(`NetServerMaxTickRate`, `NetCullDistanceSquared`, `NetUpdateFrequency`)은 1일차에 5.8.3 소스에서 직접 확인하고, 포스팅 0에 파일 경로와 함께 적는다. 위 표의 150m는 이전 버전 기준 기억값(`NetCullDistanceSquared = 225,000,000`, 즉 15,000cm)이다.

기준선 조건. 2일차에 다음을 모두 확인하고 사용자가 확정한다.

- **초기 전송 완료**: 측정 시작 전에 연결당 열린 액터 채널 수가 전체 액터 수 근처에서 멈춘다.
- **지속적인 예산 초과**: 측정 구간 프레임의 절반 이상이 틱 예산을 넘는다. P99만 넘는 것은 해당하지 않는다.
- **가장 큰 비용이 네트워크**: Insights에서 확인한다.
- **송신 한도에 포화되지 않는다**: 레거시는 연결이 송신 한도에 걸리면 뒤쪽 액터의 리플리케이션을 미룬다. 포화 상태에서는 기준선의 처리 비용이 실제보다 작게 나오고, 최적화 후 대역폭이 오히려 느는 식으로 결과를 설명하기 어려워진다. 그래서 기준선이 포화되면 프로젝트 설정에서 연결당 송신 한도를 기준선 실측 송신량의 약 두 배로 올려 고정한다(2026-10-01 결정). 네트워크가 루프백이라 부작용이 없다. 올린 값과 이유는 포스팅 0에 적는다. 기본 한도에서의 포화와 우선순위는 백로그의 별도 포스팅으로 다룬다.

재현성:

- 노드와 NPC 배치는 고정 시드로 생성한다.
- 클라이언트는 실행 인자로 자리 번호를 받는다. 접속 순서에 따라 위치가 달라지지 않는다.
- 모든 클라이언트가 준비되면 서버가 공통 시작 신호를 낸다. 클라이언트의 이동과 채집, NPC의 배회, 자동 스크린샷의 시계가 모두 이 신호에서 출발한다.
- 클라이언트는 고정 경유점을 따라 자동 이동한다.
- 클라이언트 하나는 제자리에서 검증용 노드를 반복 채집해 약 26초 주기의 상태 변화를 만든다(2초 간격 3회에 고갈, 20초 뒤 재생).
- 클라이언트는 저해상도 창과 30fps 제한으로 실행한다.
- 서버와 클라이언트를 서로 다른 물리 코어에 고정한다. 서버는 논리 프로세서 0~7, 클라이언트는 나머지를 쓴다. 최적화로 클라이언트 부하가 줄어든 효과가 서버 수치에 섞이는 것을 줄이기 위해서다.
- 스크립트 하나가 서버와 클라이언트 전부를 띄운다.

### 8.2 절차

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 준비 구간 | 접속 완료 후 30초를 버림 | 접속 직후에는 모든 액터의 초기 스폰 데이터가 한꺼번에 전송되어 정상 상태와 다르다. 2일차에 Network Insights에서 대역폭이 안정되는 시점을 확인해 조정한다. |
| 측정 구간 | 60초 | 서버가 30Hz를 유지하면 1,800프레임이다. 유지하지 못하면 그보다 적으므로 실제 프레임 수를 함께 적는다. P99는 99백분위 경계값이며 느린 1%의 평균이 아니다. |
| 반복 | 구성마다 3회, 중앙값 기록 | 한 번의 이상치를 걸러 낸다. 지속적인 경합이나 실행 순서의 영향까지 없애지는 못한다. 세 값과 변동 폭(최댓값 - 최솟값)을 모두 포스팅에 적는다. |
| 차이의 판단 | 중앙값의 변화가 두 구성의 변동 폭 중 큰 쪽보다 클 때만 차이가 있다고 적음 | 그보다 작으면 "구별하지 못했다"고 적고 두 구성을 한 번 더 측정한다. 큰 효과는 3회로 충분하고, 작은 효과에만 추가 측정을 쓴다. |
| 실패 처리 | 준비 구간 이후 연결 수가 바뀌면 그 실행은 버림 | 연결이 빠지면 송신 바이트 합계와 서버 부하가 함께 줄어, 최적화 효과로 잘못 읽게 된다. 서버가 CSV를 쓰지 않고 종료 코드 1로 끝나고, 스크립트가 실패로 처리한다. |

서버 실행 시 CPU와 네트워크 트레이스 채널을 켜서 Unreal Insights로 수집한다. 정확한 실행 인자는 1일차에 5.8.3에서 확인해 `Scripts/`에 넣는다.

### 8.3 지표

모든 포스팅이 같은 표를 쓴다. 포스팅과 README의 표에는 Insights에서 읽은 값을 쓴다.

| 지표 | 정의와 출처 | 보는 이유 |
| --- | --- | --- |
| 서버 프레임 시간 (평균, P99) | Timing Insights의 프레임 시간 | 틱 예산 33.3ms 대비 여유 |
| 리플리케이션 시간 (프레임당) | Timing Insights의 타이머 하나. 2일차에 고르고 이후 바꾸지 않는다 | 프레임 시간 중 리플리케이션이 차지하는 몫 |
| 연결당 송신 대역폭 | Network Insights. CSV 값과 대조 | 클라이언트 회선 부담과 서버 송신 비용 |
| 연결당 열린 액터 채널 수 | CSV | 서버가 연결마다 유지하는 리플리케이션 대상의 수 |
| 클라이언트에 존재하는 액터 수 | 클라이언트 화면 위 글자 | 클라이언트가 실제로 가진 것 |

열린 액터 채널 수와 클라이언트에 존재하는 액터 수는 다른 수치다. 휴면에 들어간 액터는 채널이 닫혀도 클라이언트에 남는다.

서버가 남기는 CSV에는 `work`(월드 틱 시작부터 프레임 끝까지의 경과 시간)와 `netflush`(액터 틱 종료부터 프레임 끝까지의 경과 시간)가 있다. 둘 다 경과 시간이라 스레드 대기와 스케줄링 지연을 포함하며, Insights의 프레임 시간이나 리플리케이션 타이머와 같은 값이 아니다. CSV는 에이전트의 전후 비교와 `Docs/STATUS.md` 기록에 쓰고, CSV의 열 이름 그대로 부른다. 서버는 측정 구간의 시작과 끝에 트레이스 북마크를 남겨 Insights에서 같은 구간을 볼 수 있게 한다.

### 8.4 정확성 확인

포스팅마다 최적화가 클라이언트 화면에 준 변화를 확인하고 적는다. 수동 확인용 스크립트가 클라이언트 두 개를 같은 자리에 띄운다. 예: 관련성 적용 후 노드가 나타나는 거리, 휴면 적용 후 채집 결과가 다른 클라이언트에 전달되는지, 휴면 액터가 멀어진 뒤에도 클라이언트에 남는 동작.

### 8.5 한계

포스팅 0과 README에 명시한다.

- 에디터 빌드 실행 파일을 쿠킹 없이 사용하므로 절대 수치는 출시 빌드와 다르다.
- 서버와 클라이언트가 같은 PC에서 돈다. 서로 다른 물리 코어에 고정하지만 캐시와 메모리 대역폭 경합은 남는다. 네트워크는 루프백이다.
- 수치는 같은 조건의 전후 비교로만 해석한다. "서버 코드만의 CPU 개선률"이라고 쓰지 않는다.
- 기준선은 엔진의 기본 관련성 판정을 의도적으로 끄고 연결당 송신 한도를 올린 인위적인 출발점이다.
- AI NPC는 움직이는 리플리케이트 액터의 대역이다. 길 찾기나 행동 트리 같은 AI 비용은 측정하지 않는다.
- 채집 RPC는 자동 실험용이다. 서버가 대상 탐색과 거리 검사, 호출 간격 제한을 하지만 그 밖의 악의적 호출은 막지 않는다.

### 8.6 시각 자료

포스팅마다 시각 자료를 적극적으로 모은다. 리플리케이션 최적화는 수치만으로는 와닿지 않으므로, 클라이언트가 실제로 무엇을 받고 있는지를 그림으로 보여준다.

| 자료 | 만드는 방법 | 담당 |
| --- | --- | --- |
| 화면 위 글자 | 모든 클라이언트가 자신에게 존재하는 노드 수와 NPC 수를 화면에 표시 | 코드 |
| 내려다보기 화면 | 클라이언트 하나가 위에서 내려다보며, 자신에게 존재하는 노드와 NPC 위치에 색 점을 그림 | 코드 |
| 자동 스크린샷 | 3인칭 클라이언트 하나와 내려다보기 클라이언트가 공통 시작 신호 이후 15초마다 저장. 같은 순번은 같은 시점이다 | 코드, 에이전트가 골라 포스팅에 넣음 |
| 수치 차트 | GitHub가 그려 주는 Mermaid 막대 차트 | 에이전트 |
| Insights 전후 스크린샷 | Timing Insights, Network Insights | 사람 |
| 전후 영상 | 10초 안팎의 화면 녹화 | 사람 |

내려다보기 화면의 전후 비교가 각 포스팅의 대표 이미지다. 화면 표시와 스크린샷의 비용은 클라이언트에 들고, 클라이언트가 가진 액터 수에 따라 달라진다. 그래서 구성마다 클라이언트 부하가 다르다. 서버와 클라이언트의 코어를 분리해(8.1절) 이 차이가 서버 수치에 섞이는 것을 줄인다.

내려다보기 클라이언트의 카메라 위치가 서버의 관련성 판정 기준으로 쓰이지 않게 한다. 서버는 폰 위치를 기준으로 판정해야 한다.

## 11. 작업 방식

구현은 AI 코딩 에이전트에게 폴더째 위임한다. 개발 속도가 최우선이므로 프로세스는 최소로 둔다.

### 11.1 위임을 위한 문서

| 파일 | 역할 |
| --- | --- |
| [AGENTS.md](../../AGENTS.md) | 에이전트의 진입점. 규칙, 완료 확인 방법, 사람에게 넘기는 일 |
| [STATUS.md](../STATUS.md) | 현재 상태, 확정된 수치, 측정 결과, 다음 할 일. 세션을 끝낼 때마다 갱신 |
| 구현 계획 문서 | 일차별 체크리스트 |
| [backlog.md](backlog.md) | 이슈 관리를 대신한다. 작업 단위는 포스팅 하나다 |

단위 테스트, CI, PR, 워크트리, 외부 이슈 트래커는 쓰지 않는다. main에 직접 커밋한다.

### 11.2 하네스

에이전트가 사람 없이 작업 결과를 검증할 수 있게 하는 데에만 투자한다.

- **빌드 스크립트**: 명령 하나로 빌드한다.
- **시나리오 스크립트**: 명령 하나로 서버와 클라이언트 전부를 띄우고, 측정이 끝나면 전부 종료한다. 서버 종료 코드와 새 CSV 행을 확인해, 실패한 실행을 성공으로 돌려주지 않는다. 같은 라벨의 재사용을 막는다.
- **수치 자동 기록**: 서버가 측정 구간(8.2절) 동안 프레임 시간과 네트워크 통계를 모아 CSV로 남기고 스스로 종료한다. 에이전트는 이 CSV로 전후를 비교한다. Insights 트레이스는 같은 실행에서 함께 수집해 사람이 분석한다.
- **시각 자료 자동 수집**: 클라이언트가 화면 표시와 스크린샷을 스스로 남긴다(8.6절). 에이전트가 이미지를 열어 보고 포스팅에 넣는다.
- **에디터 작업 최소화**: 액터는 모두 C++로 작성하고, 자원 노드와 AI NPC는 실행 시 코드로 생성한다.

CSV와 Insights 수치의 관계는 2일차에 한 번 대조해 포스팅 0에 적는다. 두 값은 정의가 다르다(8.3절).
