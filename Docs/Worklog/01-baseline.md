## 2026-10-02 태스크 10.3: Insights 값과 후보 기법 자료 (`baseline3-r1`\~`r3`)

태스크 10.3을 끝냈다(2026-10-02). 에이전트가 `baseline3-r1`\~`r3`의 트레이스를 Insights로 직접 열어 측정 구간의 값을 읽고, [후보 기법 자료](../../Posts/01-baseline/candidates.md)에 정리했다. 코드와 빌드, 시나리오 실행은 하지 않았다.

- **Insights 값과 CSV가 세 실행 모두 맞는다.** 서버 프레임 시간 198.44 / 204.82 / 179.47ms와 `work_avg_ms` 198.773 / 205.150 / 179.673(-0.11\~-0.17%), 리플리케이션 시간(`GameNetDriver` 프레임당 Incl) 188.97 / 194.69 / 171.89ms와 `netflush_avg_ms` 189.375 / 195.108 / 172.293(-0.21\~-0.24%). 연결당 송신 대역폭(Network Insights 내용 기준, `Connection 0`)은 `r1` 28,048, `r3` 31,012바이트/초로 CSV `out_bytes_per_sec_per_conn`(28,896, 31,990)보다 3.0%, 3.2% 작다.
- **내역(`r1`).** `GameNetDriver`가 `WorldTick`의 95.17%다. 그 안에서 `LabResourceNode` 52.14%(호출 12,082,416 = 5,001 × 8 × 302), `LabNpc` 10.31%, `GameNetDriver` 자체(Excl) 37.0%다. 송신 비트의 76.0%가 `LabNpc`이고 `LabResourceNode`는 60초에 576비트다.
- **고려, 직렬화, 송신으로는 일부만 나뉜다.** 클래스 이름 타이머는 `UActorChannel::ReplicateActor`(`DataChannel.cpp:3622-3625`)라서 직렬화가 보이고, 고려 목록, 연결마다의 우선순위 정렬, `Connection->Tick`의 송신은 모두 Excl에 섞인다(`NetDriver.cpp:1174`). 타임라인에서 `GameNetDriver` 아래가 연결 8개의 덩어리로 보이고 덩어리 앞마다 자식 타이머 없는 3.6\~5.2ms 구간이 있다(프레임 하나를 눈금으로 어림). 나누는 실행(`-statnamedevents`)은 [backlog.md](../Planning/backlog.md)에 적었다.
- **세 실행의 구성이 같다.** 호출 횟수(액터 수 × 연결 수 × 프레임 수), 프레임당 송신(약 5,570\~5,580바이트), 구성 비율(Excl 37.0\~37.1%)이 같고, 느린 실행은 모든 하위 타이머가 1.12\~1.18배 느리다(`r2` ÷ `r3`). 흔들림의 원인은 여전히 모른다.
- **스크린샷 후보 8장**을 `Posts/01-baseline/images/insights-*.png`로 저장했다(목록은 candidates.md 8절).
- 엔진 소스 위치는 서브에이전트가 찾고 에이전트가 인용한 줄을 다시 읽어 확인했다.
- **Insights 캡처를 다시 찍었다(사용자 지적).** 화면 복사로 찍은 캡처에 에이전트 조작 중 화면 가장자리의 주황 테두리가 들어가 있었다(가장자리 픽셀 115,78,66 근처). 창 내용만 찍는 `Scripts/capture-insights.ps1`(`PrintWindow`, 툴팁 포함)을 만들어 `Posts/01-baseline/images/insights-*.png` 8장과 테스트베드의 `timing.png`, `network.png`를 같은 장면으로 다시 찍었다(가장자리 54,54,54). `Docs/Guides/images/insights-calib-f/`의 10장은 테두리가 남아 있고 다시 찍지 않았다(사용자 결정).

## 2026-10-02 화면 녹화를 에이전트가 맡음 (`Scripts/capture-video.ps1`)

화면 녹화를 에이전트가 맡게 했다(2026-10-02, 사용자 결정). ffmpeg 9.0.2를 설치하고(`winget install --id Gyan.FFmpeg -e`) `Scripts/capture-video.ps1`을 만들었다. 화면 복제 API(ddagrab)로 받아 GPU 인코더(h264_nvenc)로 넣고, MP4, GIF, WebP와 한 장짜리 PNG를 남긴다. `-Window`로 고른 창은 녹화하는 동안 맨 위로 올린다. 처음 녹화에서 왼쪽 클라이언트 창이 이 앱 창에 가려 앱 창이 찍혔기 때문이다. 녹화가 끝나면 6프레임 미리보기를 `Saved/Screenshots/Lab/`에 남긴다. `run-manual.ps1`의 두 클라이언트를 6초 찍은 GIF는 1.77 MB, MP4는 1.22 MB였고, 미리보기에서 두 창이 모두 찍힌 것을 확인했다. 지침도 바꿨다(AGENTS.md, 구현 계획 "시각 자료 규칙"과 태스크 9.4, 11.6, 설계 문서 8.6, 11.3).
- 찍기 전에 무엇을, 어느 실행에서, 몇 초, 어느 파일 이름으로 찍는지 채팅에 적고 허가를 받는다. 화면을 그대로 받아서 사용자의 다른 창이 찍힐 수 있기 때문이다.
- 수치를 쓰는 측정 실행에서는 찍지 않는다. 8개 창이 필요하면 시각 자료 전용 라벨(`visualN`)로 실행하고 `-AllowMeasuring`을 준다. `visualN`의 수치는 비교에 쓰지 않는다.
- 전후 영상은 자동 이동 클라이언트의 정해진 경로를 찍는다. 영상은 GIF(폭 960px, 15fps)로 넣는다.

## 2026-10-02 태스크 10.4\~10.7: 포스팅 1 완료 (`baseline3`)

태스크 10.4\~10.7을 끝내고 [포스팅 1](../../Posts/01-baseline/README.md)을 완료했다(2026-10-02). 코드와 빌드, 시나리오 실행은 하지 않았다.

- **기법 순서(사용자 결정).** 포스팅 2 관련성 → 포스팅 3 자원 노드 휴면 → 포스팅 4 NPC 업데이트 빈도. README 포스팅 표의 기존 번호와 같다.
- **"관찰"과 "선택"(태스크 10.4).** 사용자가 인터뷰로 판단을 주고, 에이전트가 문장으로 옮긴 초안을 사용자가 검토해 승인했다(사용자 결정). 가장 큰 비용은 변하지 않는 자원 노드를 매 프레임 확인하는 일(`LabResourceNode` 52.14%, 60초에 576비트), 비용 분해는 "일부만 나뉜다"(추정은 추정으로 표기), 구현하지 않는 후보 셋은 버린 이유를 한 줄씩 적었다.
- **Insights 이미지에 번호 상자를 그렸다(사용자 요청).** 새 스크립트 `Scripts/annotate-image.ps1`이 원본 좌표로 노란 4px 외곽선 상자를 최대 3개 그리고 번호(①②③)를 단다. 처음에는 주황이었으나 Insights의 빨강, 갈색 행 바탕에 묻혀 노랑으로 바꿨고, 검은 테두리는 쓰지 않는다(사용자 결정). 원본 `insights-r1-*.png`는 그대로이고, 포스팅에는 `timing.png`, `network.png`, `packet.png`를 넣었다. 본문은 번호로 값을 가리킨다. 구현 계획 "시각 자료 규칙"에 한 줄을 더했다.
- **자동 스크린샷 순번(태스크 10.5).** 3인칭은 순번 04(t=75s), 내려다보기는 순번 02(t=45s)다. **포스팅 2\~4의 전후 이미지도 이 순번을 쓴다.** 3인칭 04는 검증용 노드가 캐릭터 앞에 서 있다(00, 02, 03은 노드가 고갈되어 보이지 않는다). 내려다보기 02는 가장자리까지 점이 차 있고 고갈된 노드의 검은 점이 보인다. 두 순번 모두 측정 구간(시작 신호 뒤 30\~90초) 안이고, 열 장 모두 `nodes=5001 npcs=300`이다.
- **나머지 섹션(태스크 10.6).** 요약, 적용(두 줄의 `bAlwaysRelevant = true`, ADR-0003, 복원과 개선의 구분), Iris에서는(엔진 소스 `BaseEngine.ini:1498, 1512`, `NetActorFactory.cpp:659`, `EngineReplicationBridge.cpp:242-253`, 미검증 표기), 결과(기준선 조건, Insights 값과 CSV, Mermaid 차트 3개, 자동 스크린샷), 한계와 다음(관련성 예고)을 썼다.
- **README(태스크 10.7).** 포스팅 표 1번을 링크와 "완료"로, 순서 문장을 "가설"에서 "정했다"로 바꾸고, 누적 수치에 기준선 줄과 Mermaid 차트 3개를 넣었다. 연결당 송신 대역폭은 `r2`를 읽지 않아 중앙값 실행 `r1`의 값(28,048바이트/초)을 썼다.
- [후보 기법 자료](../../Posts/01-baseline/candidates.md) 8절에 포스팅에 넣은 이미지와 상자를 적었다.
- **서버 프레임 시간 P99를 Insights에서 읽어 채웠다(사용자 요청).** Timers 패널에는 백분위가 없어서 `TimingInsights.ExportTimingEvents`로 GameThread `Frame` 이벤트를 창 없이 내보내고(`UnrealInsights.exe -NoUI -AutoQuit`), 두 북마크에 걸친 이벤트의 길이를 정렬해 ceil(N × 0.99)번째 값을 읽었다. 절차는 [insights-reading.md](../Guides/insights-reading.md)의 "P99 읽기"에 있다. 고른 이벤트 수가 Timers 패널의 `Frame` Count와 같고(303 / 293 / 335), 같은 이벤트의 평균이 서버 프레임 시간(198.44 / 204.82 / 179.47ms)과 같다. P99는 268.70 / 239.05 / 262.97ms(중앙값 262.97, `r3`, 변동 폭 29.65)이고 `work_p99_ms`(268.485 / 238.737 / 262.736)와 +0.08\~+0.13% 차이다. 경계 프레임을 넣든 빼든 값이 같다. 포스팅 1의 요약과 결과, README 누적 수치, candidates.md 1절에 넣었다.
